## ⭐⭐⭐ 微信扫二维码提示"下载文件"（根因 + 修复）

### 现象
用 `生免仪器二维码.pdf` / `临检组维修记录二维码.pdf` / `分子组维修记录二维码.pdf`
这三个 A4 二维码文件，**微信扫码后提示下载文件**，而不是打开维修记录填报页。
"之前生成的二维码不是这样的"。

### 排查过程
**1. 先确认二维码内容对不对**（别一上来就改代码）
```python
# 用 fitz 提图 + cv2 解码（cv2 已在本地 venv）
d = fitz.open(pdf)
for im in d[0].get_images(full=True):
    info = d.extract_image(im[0])
    v, pts, _ = cv2.QRCodeDetector().detectAndDecode(np.array(Image.open(BytesIO(info['image'])).convert('RGB')))
# → https://...run.tcloudbase.com/repair-fill?code=MHZYY-JYK-SM-1016  ✅ 链接完全正确
```
3 个 PDF 分别是 SM/LJ/WSW 三个专业组，编号规则一致，链接都对。

**2. 测响应头**（关键）
```bash
curl -s -D - -o /dev/null "$H/repair-fill?code=..."
# → content-disposition: attachment        ← 微信据此判定"下载文件"
# → content-type: text/html; charset=utf-8
```

### ⭐ 根因：**CloudBase 网关强制加 `Content-Disposition: attachment`**
对比测试发现**所有页面**（含首页 `/`）都是 attachment：
```
/            → content-disposition: attachment
/instruments → content-disposition: attachment
/repair-fill → content-disposition: attachment
```
而代码 `main.py::spa_fallback` **本来已经写了** `content_disposition_type="inline"`，
并有注释说明这个问题 —— **但网关把应用层的设置覆盖了**，应用层根本控制不了。

### 修复：改用 `Response` 直接回 bytes，**根本不设置该头**
```python
from starlette.responses import Response as _RawResponse
return _RawResponse(
    content=index.read_bytes(),
    media_type="text/html; charset=utf-8",
    headers={"Cache-Control": "no-store, ...", "X-Robots-Tag": "noindex, ..."},
)
```
**原理**：Starlette 只有在 `FileResponse` 传了 `filename` 时才发
`content-disposition`，不传就不发；用普通 `Response` 连这个头都不会出现 → 网关也没"可覆盖"的东西。

**本地验证**：`r.raw_headers` 里确认无 `content-disposition` ✓

### 提交
- `08bbc2d7` fix(frontend): SPA fallback 去掉 content-disposition

## ⭐⭐ 关键发现：`content-disposition: attachment` 不是网关加的！

### ⭐⭐ 判据（超好用，以后直接用）
**连 API 接口（`application/json`）都带 `content-disposition: attachment`：**
```
/api/v1/public/repairs/by-code/MHZYY-JYK-SM-1016
   → content-type: application/json
   → content-disposition: attachment      ← 网关不会给 JSON 加下载头！
```
**网关只对 HTML 页面加这个头，不�� JSON 加。**
→ 所以**这是我们的代码加的**（旧镜像里的旧 `FileResponse` 逻辑），
   **不是网关覆盖**。之前"网关强制覆盖"的判断是**错的**。

### 正确的排查顺序（下次别再绕弯路）
```bash
# 1. 先看镜像 tag 时间 vs 我的提交时间（判断代码上没上线）
tcb cloudrun detail -e <env> -s <svc> | grep ImageUrl     # tag 时间 < 提交时间 → 没上线
# 2. 再测 API 接口有没有该头（判断来源）
curl -s -D - -o /dev/null "$H/api/v1/xxx" | grep -i content-disposition
#   JSON 也有 → 我们自己的代码
#   只有 HTML 有 → 真的是网关
# 3. 加随机串绕缓存再测
curl -s -D - -o /dev/null "$H/repair-fill?code=xxx&_cb=$(date +%s)"
```

## ✅✅ 结论确认：微信提示下载 = 二维码用了 **http://**

### 用户验证
生成 https 版测试 PDF（`outputs/测试二维码_3张.pdf`）→ 微信扫码**正常打开填报页** ✓
→ 根因确定：**协议是 http，不是响应头的问题。**

### ⭐⭐⭐ 核心教训（务必记住）
```python
# ❌ 错误写法
host = str(request.base_url)
```
**CloudBase 前面挂的是 http 反向代理**，`request.base_url` 会从请求 scheme 推导
→ 拿到 **`http://`** → 微信扫码**提示下载文件**（而不是打开网页），
→ 而且**服务器响应头完全一样**（我测了 http/https 都是
  `content-disposition: attachment`），**光看响应头查不出原因**。

```python
# ✅ 正确写法
host = (os.getenv("LAB_PUBLIC_HOST") or str(request.base_url)).rstrip("/")
if host.startswith("http://"):                 # 强制升级
    host = "https://" + host[len("http://"):]
```
**凡是生成二维码/分享链接，一律强制 https。**

### 排查这个问题的正确顺序（下次照做）
1. **先解码二维码看内容**（别先动代码）

3. **再用 curl 对比两种协议的响应头** → 发现一样 → 说明不是响应头问题
4. 生成 https 版让用户实际扫码验证 ← **这一步最关键，别自己猜**

## ⭐⭐⭐ 二维码 PNG 缓存"冻住"了修复（第二层坑）

### 现象
`_card_host()` 已强制 https、代码已部署、镜像 tag 已是最新（13:20），
但**下载线上卡片集解码，二维码还是 `http://`**。

### 根因：二维码 PNG 磁盘缓存
```python
def _make_qr_png(url, path):
    if os.path.exists(path):     # ← 命中就复用
        return path
```
而缓存文件名**只按仪器编号**：`MHZYY-JYK-SM-1001.png`（**不含协议/主机**）
→ 容器重建前 **http 时代生成的旧 PNG 还在磁盘上**
→ 每次生成卡片都命中旧文件 → **代码改了也不生效**（被缓存冻住）

### 修法：缓存 key 加 URL 指纹
```python
import hashlib
sig = hashlib.md5(url.encode('utf-8')).hexdigest()[:8]
png = _make_qr_png(url, os.path.join(qr_dir, f'{full}_{sig}.png'))
```
协议/主机一变 → 指纹变 → 自动生成新图，不命中旧缓存。

**本地验证方法**（好用）：故意造一个"旧命名"的 PNG 放进去，再跑一遍，
确认仍输出正确的新内容（而不是被旧文件替换）。

```python
shutil.copy(sample_png, 'd:/tmp_qrtest/MHZYY-JYK-SM-1001.png')  # 旧命名
build_pdf(items, 'https://...', 'd:/tmp_qrtest')
# → 输出 https ✓，且目录里多出 MHZYY-JYK-SM-1001_293edc3c.png
```

### ⭐⭐ 通用教训（务必记住）
**凡是有磁盘/内存缓存的地方，缓存 key 必须包含所有会影响内容的参数。**
只用一个"看起来唯一"的字段（如编号）做 key，改了其他配置（域名/协议/样式）缓存也不失效。
