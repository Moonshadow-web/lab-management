## 质控上传规则解析【关键 bug 修复】（commit `67033c3`）
- **现象**：AU5800 等 LIS 导出含规则列（如「失控规则」），原表标了很多失控点（β2微球蛋白 1-3S、10-x 等），但系统没解析出来。
- **根因**：上轮 step1.5 把「解析失败」与「空单元格」混为一谈。一旦 rule_column_present=True，任何未解析的单元格都被强制清零为在控并冻结 R-4s —— 而 LIS 规则值写法（1-3S(失控)、10-X、1－3S 全角、13S 无连字符等）恰不被旧解析器识别，于是 LIS 标过的失控点被全部抹掉。
- **修复**：
  1. 仅「真正空」单元格在含规则列时判在控；有内容但未识别的单元格保持后端 Westgard，不误翻。
  2. 解析器增强：全角/异形标点(－～–:)转半角、去外层括号、子串提取（1-3S(失控)/失控1-3S）、无连字符写法(13S/10X)。
  3. 上传响应新增 `rule_cells_total/recognized/unrecognized` 诊断计数，便于核对 LIS 写法是否被识别。
- **数据恢复**：原上传已把原始规则串存进 `qc_daily_values.uploaded_rule`，且 rule_column_present 已落库；修复部署后直接调用 `POST /qc-summaries/_recalc`（admin/qc_manager）即可用新解析器重算，无需重新上传（前提是当时规则列被识别、rule_column_present=True）。若 rule_column_matched=False 则需重新上传。
- 测试 11→14 断言全过（用例H 未识别写法→保留后端；用例I/J 写法变体解析）。

## 质控上传 500 故障（commit `95e3fd2`）
- **现象**：质控 LIS 数据上传返回 500（Request failed with status code 500）。
- **根因推断**：上一轮 QC 部署（含 `rule_column_present` 模型列，commit `6ae817d`/`67033c3`）因镜像推送 broken pipe 中断且任务被清理、未确认成功，线上服役容器仍是更早的 `scheduling-v7-matrixwidth` 构建（build 标记从未随 QC 提交更新）。结果：代码引用了 `qc_monthly_summaries.rule_column_present` 列，但非空的线上 MySQL 表缺该列 → 上传时 `Unknown column` → 500。
- **注意**：`main._migrate_schema` 的 `alters` 字典块只跑 SQLite `PRAGMA`，**MySQL 下完全不生效**；非空线上表的补列只能靠 `_ensure_missing_columns()`（dialect 无关）。当该次部署中断时，补列没执行。
- **修复**：在 `_ensure_missing_columns()` 末尾**显式兜底补列** `qc_monthly_summaries.rule_column_present` 与 `qc_daily_values.uploaded_rule`（幂等）；并把 `diag._BUILD_MARK` 改为 `qc-ruleparser-fix2-2026-07-26`，使 `curl /_diag/build` 能确认新代码是否生效。
- **部署铁律强化**：每次改模型/解析/关键逻辑提交，**必须同步改 `_BUILD_MARK`**，且部署后必须 curl 内网 `_diag/build` 核对标记；broken pipe 等中断需重试至确认成功，不能只看任务被清理就假定成功。
- 状态：95e3fd2 已 push，重部署中（任务 uDkK4d）。
