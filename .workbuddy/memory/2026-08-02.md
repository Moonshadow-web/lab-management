## 文件评审删除失败（管理员也中招）真正根因（2026-08-02）
用户反馈"管理员也删除失败"。排查发现：带分配的评审计划走**标准 `DELETE /review/campaigns/{id}`（make_router 自带、非级联）会因 review_assignments 外键约束 500**；旧版前端调用的就是这个端点，故 admin 同样失败（admin 不被 FK 豁免）。当前前端已改调 `/cascade`，但只要浏览器缓存旧 `review.js` 就继续 500。
- 根治：移除 campaign_router 自带的非级联 DELETE，把 `DELETE /review/campaigns/{cid}` 与 `/review/campaigns/{cid}/cascade` 都指向同一级联删除函数（先删 review_records、review_assignments，再删 campaign）。本地路由表确认旧 DELETE 已移除、裸路径已级联。
- 验证：线上裸路径删除临时计划（含分配/接收状态/记录）返回 `{"ok": true}` 且列表中消失；此前同操作必 500。
- 提交 `6c61a85`，deploy 后 build mark `review-campaign-bare-delete-cascade-2026-08-02`。
- 结论：现在无论前端 JS 新旧，文件评审计划删除均可用；无需再依赖用户硬刷新。

## 测试数据污染教训（2026-08-02 重要）
本轮为复现"删除失败"多次用 admin 创建 `__tmp_*` 评审计划、把真实文档分配进去、写 A-027 记录，部分临时计划未及时清理，导致用户在生产界面看到 `__tmp_bare_del__`(乱码名) 和"孕酮试剂盒说明书 项目说明书"污染。
- 教训：在**生产环境**用真实 admin 账号做破坏性/污染性验证时，必须：(1) 测试后立即级联清理所有 `__tmp_*` 计划+分配+记录+临时用户；(2) 创建前先记录，结束时 `DELETE /review/campaigns/{id}` 清理并确认列表无残留；(3) 尽量不要用真实文档做分配测试，或只用后立即删。已被用户发现两次（删失败截图 + 乱码计划）。
- 已养成：每次测试后扫一遍 `__tmp_*` 计划与用户并清理。
