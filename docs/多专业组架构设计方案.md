# 多专业组架构设计方案

> 目标：在**不影响生免组现有全部功能**的前提下，让临检组 / 微生物组 / 分子组 / 血库也能使用本系统。
> 版本：v1（2026-09-12）　状态：待确认

---

## 一、现状（改造前）

| 层 | 现状 | 说明 |
|---|---|---|
| 用户 | `users` 表有 `role` / `roles` / `department`，**没有"专业组"概念** | 现有用户 = 生免组人员 |
| 菜单 | 路由 `meta.moduleKey` + 权限表 `roles → modules` 映射（`auth.canAccessMenu`） | admin 全可见；普通职工按角色模块放行 |
| 数据 | 业务表（项目库、文件、仪器、质控、试剂、排班…）**无组维度** | 全库数据都属于生免组 |
| 登录 | 用户名 + 密码 → JWT | 无组选择 |

**结论：系统是"单租户"结构，需要引入"专业组"作为数据域。**

---

## 二、目标架构

### 2.1 引入"专业组"（group_code）

| group_code | 专业组 | 初始数据 |
|---|---|---|
| `sm` | 生免组 | 保留现有全部数据 |
| `lj` | 临检组 | 空 |
| `wsw` | 微生物组 | 空 |
| `fz` | 分子组 | 空 |
| `xk` | 血库 | 空 |

新建字典表 `lab_groups`（组编码、组名称、排序、是否启用），便于以后加组。

### 2.2 入口：登录页选择专业组

```
登录页
 ┌──────────────────────────────┐
 │  民航总医院检验科 管理系统      │
 │  专业组：[ 生免组 ▾ ]          │  ← 新增：选择专业组
 │  用户名：[__________]          │
 │  密　码：[__________]          │
 │        [ 登 录 ]              │
 └──────────────────────────────┘
```

- 登录请求携带 `group_code`；后端校验**该用户是否属于所选组**（管理员可进入任意组）
- 签发 JWT 时写入 `active_group`
- 顶栏显示当前专业组；**管理员/多组用户**可在顶栏切换组（普通用户不可切）

### 2.3 菜单与功能可见范围

| 模块 | 生免组 | 临检/微生物/分子/血库 | 说明 |
|---|---|---|---|
| 工作台 | ✅ | ✅（简化版） | 显示本组概览 |
| 项目查询 | ✅ | ✅ **空**（自行录入） | 按组隔离 |
| 文件管理 | ✅ | ✅ **空** | 按组隔离 |
| 仪器档案 | ✅ | ✅ **空** | 按组隔离 |
| 质控 / 试剂 / 人员能力 / 性能验证 / 排班 / 15189 / 到货接收 / 仪器关联等 | ✅ | ❌ 默认隐藏 | 后续按需逐组开放 |
| 用户管理 / 权限配置 / 审计日志 | 仅 admin | **仅 admin** | 与组无关，全局功能 |

实现方式：路由 `meta.groups`（允许的组）+ `meta.adminOnly`（已有）两者叠加判定，**不改动现有权限算法**。

### 2.4 数据隔离方式

**方案：单库 + 行级隔离（推荐）**

- 所有业务表增加 `group_code VARCHAR(20) NOT NULL DEFAULT 'sm'`（**存量数据自动归属生免组**）
- 后端统一依赖：`current_group`（从 JWT 取），所有 list/create/update/delete 自动带组过滤
- 索引：`(group_code, ...)` 组合索引，保证性能
- 不采用"一组建一套库/表"——运维成本高、CloudBase 单实例更适合行级隔离

### 2.5 兼容策略（核心：不破坏现有功能）

1. **默认值 = 生免组**：`group_code` 默认 `sm`，老数据、老账号、老链接行为**完全不变**
2. **过滤放行规则**：`active_group` 为空 或 为 `sm` 时，后端按"不过滤"处理（等价于现状），**零回归风险**
3. **权限体系不动**：`roles → modules` 原样保留，只新增"组"这一层数据域
4. **扫码链接**：维修二维码按仪器编号定位，仪器自带组，无需改链接格式；如后续其他组也用，二维码自动带出该组仪器
5. **分阶段上线**：每阶段独立可部署、可验收、可回滚（见下）

## 三、实施阶段（每阶段独立部署与验收）

| 阶段 | 内容 | 验收点 | 回归风险 |
|---|---|---|---|
| **S1 基础层** | 建 `lab_groups` 表 + 各业务表加 `group_code`（默认 sm）；用户表加 `group_code` | 服务正常启动；生免组数据条数不变；老功能可用 | 极低（只加列） |
| **S2 登录与身份** | 登录页加"专业组"下拉；JWT 带 `active_group`；顶栏显示/切换 | 生免组账号登录后功能与现在完全一致 | 低 |
| **S3 读写隔离** | 后端按组过滤（先覆盖 项目库 / 文件 / 仪器档案 三个模块） | 生免组看到原数据；其他组看到空列表；新建数据落到本组 | 中（需回归测试） |

## 五、已确认决策（2026-09-12）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 用户与组的关系 | **一人一组**；管理员账号可进任意组 |
| 2 | 其他组基础数据 | **初始为空**，后续由管理员提供数据、批量导入（预留导入脚本/入口） |
| 3 | 仪器与文件的跨组共享 | **按编号规则共享**：编号中含 `KS` 段（如 `BG-KS-…`、`MHZYY-JYK-KS-…`）视为**科室共享**，所有组可见可查；其余按组隔离 |
| 4 | 其他组模块范围 | **工作台 + 项目查询 + 文件管理 + 仪器档案 + 试剂管理（试剂目录/实时库存/盘库/月消耗/项目与仪器关联）+ 到货接收**；其余模块菜单结构预留但**不显示**，后续按组逐步开放 |

### 5.1 其他 4 组的菜单（最终）

```
工作台
项目查询        ← 空，自行录入
文件管理        ← 空，自行录入（能看到 KS 共享文件）
仪器档案        ← 空，自行录入（能看到 KS 共享设备）
试剂管理  ▾     ← 试剂目录 / 实时库存 / 盘库管理 / 月消耗 / 项目与仪器关联
到货接收        ← 本组试剂到货登记与确认
（隐藏预留：质控管理、人员能力管理、性能验证、排班管理、15189专项、项目质量要求、岗位仪器匹配…）
用户管理 / 权限配置 / 审计日志 → 仅管理员
```


### 5.2 编号与共享规则（细化）

| 对象 | 生免组专属 | 科室共享 | 其他组（未来） |
|---|---|---|---|
| 仪器编号 `dept_no` | `MHZYY-JYK-SM-xxxx` | `MHZYY-JYK-KS-xxxx` | `…-LJ-` / `…-WSW-` / `…-FZ-` / `…-XK-` |
| 文件编号 `doc_number` | `BG-SM-…` / `SM-SOP-…` | `BG-KS-…` | `BG-LJ-…` 等 |
| 文件目录 | 生免组记录表格 | 0科室共用表格 | 各组自有目录 |

**列表查询规则**
- 当前组 = `sm`（或为空）→ **不过滤**（与现在完全一致，保证零回归）
- 当前组 = 其他组 → `WHERE group_code = 当前组 OR 编号含 KS 段`（能看到本科室共享的设备与文件，看不到生免组专属数据）
- 新建数据 → 强制写入当前组；`KS` 共享数据仅**管理员**可维护

### 5.3 预留入口的实现方式（改配置即可开放）

菜单与路由保留全部条目，用 `meta.groups` 控制可见性：

```
生免组：groups 含 'sm'（全部模块）
其他组：test-items / documents / instruments / reagents / reagent-receivings
        这些 meta.groups 含本研究组代码（其余模块不含）
预留（暂不显示）：qc、reagent、training、verification、scheduling、iso15189、eqa-associations…
→ 后续只需在 meta.groups 里补上组代码即可对该组开放，无需改代码结构
```

## 六、风险清单与预防措施（重点：避免功能不可用）

> 本次改造是"给运行中的系统动骨架"，风险主要来自 5 处：**批量改表、统一过滤、唯一约束、登录态、部署方式**。
> 下表逐条给出**触发条件 → 后果 → 预防 → 验证方法**，实施时逐项打勾。

### R1 批量给业务表加列导致部署失败／锁表（高危）

| 项 | 内容 |
|---|---|
| 触发 | 一次性给 25–30 张表 `ALTER TABLE`（质控/患者数据表可能几十万行） |
| 后果 | 建列超时 → 启动自愈失败 → **容器崩溃重启、服务不可用**（历史上已因类似原因崩过） |
| 预防 | ①**分 3 批**：先小表（字典类）→ 再中等表 → 最后大表（质控/结果类）②每批单独部署并验证 ③列定义统一 `VARCHAR(20) NOT NULL DEFAULT 'sm'`（带默认值加列不锁全表）④自愈逻辑保持幂等 + try/except，单列失败不阻断启动 |
| 验证 | 每批部署后：`tcb cloudrun record list` 状态 normal + `/api/v1/_diag/build` 200 + 抽查表结构含 group_code + 首页可登录 |

### R2 统一过滤逻辑误伤生免组（高危）

| 项 | 内容 |
|---|---|
| 触发 | 后端为了多组，把 list/create 全量改成"必须带组" → 生免组老数据被过滤掉 |
| 后果 | **生免组看不到自己的数据**（最严重） |
| 预防 | ①`make_router` 增加 `group_scoped` 开关，**默认 False（=现状）**，逐模块打开 ②过滤规则：`当前组为空 或 == 'sm'` → **不附加任何条件** ③先开 项目/文件/仪器 三个模块，验证后再开试剂/到货 |
| 验证 | 每个模块"打开开关"前后，用接口对比**生免组列表总数一致**（写脚本自动比对，不一致立即回滚） |

### R3 唯一约束冲突（高危，最易引发线上插入失败）

| 项 | 内容 |
|---|---|
| 触发 | 现有唯一索引（如 `test_items.code`、`exam_banks.post`、`users.username`、试剂目录编号等）在加入多组后，**不同组用同一个编号**会插入失败 |
| 后果 | 其他组录入时 500 / 报"已存在" |
| 预防 | ①**先清点全部唯一索引**（脚本扫 model 的 `unique=True` 与 `__table_args__`）②改为**复合唯一** `(group_code, code)`：`DROP INDEX uq_x ON t; CREATE UNIQUE INDEX uq_x ON t(group_code, code)` ③对共享字典类（如仪器编号），保持全局唯一并明确"编号即身份" |
| 验证 | 故意在临检组插入与生免组**同名编号**的记录，应成功；同组内重复应被拒 |

### R4 存量数据未回填 / NULL 组导致数据"消失"（中危）

| 项 | 内容 |
|---|---|
| 触发 | 加列允许 NULL，或先加列后回填失败 |
| 预防 | 加列即 `NOT NULL DEFAULT 'sm'`（MySQL 自动回填存量行）；不单独跑回填脚本 |
| 验证 | `SELECT COUNT(*) WHERE group_code IS NULL OR group_code <> 'sm'` 应为 0 |

### R5 登录态与老令牌兼容（中危）

| 项 | 内容 |
|---|---|
| 触发 | JWT 新增 `active_group`，老令牌无该字段 |
| 预防 | ①解析时**缺失即默认 `sm`** ②登录页新增组选择但**账号密码逻辑完全不动** ③切换组后前端 `reset` 全部 store 并重载页面，避免显示上一组缓存 |
| 验证 | ①用旧令牌访问接口应正常（视为生免组）②切换组后列表/统计立即刷新，不残留旧数据 |

### R6 公开链接（维修二维码 / 扫码答题）与组的关系（中危）

| 项 | 内容 |
|---|---|
| 风险 | 维修二维码按仪器编号定位；KS 共享设备可能被多组维修 |
| 规则 | ①二维码链接**不变**（`?code=编号`），天然按仪器定位 ②维修记录写入**仪器所属组**；KS 共享设备写入**提交人所在组**（无登录时写入仪器所属组） ③扫码答题按考核单 id，不受组影响 |
| 验证 | 用其他组的设备编号扫码 → 能正常提交；记录出现在该设备所属组的列表里 |

### R7 角色与组叠加（中危）

| 项 | 内容 |
|---|---|
| 触发 | 到货接收角色（配送员）服务全科，若按组过滤会导致看不到其他组的货 |
| 规则 | ①`reagent_delivery`（配送）角色：**到货接收列表跨组可见**（其职责是院内配送）②其他角色：按组 ③试剂管理各列表：按组 |
| 验证 | 用配送角色账号检查能看到所有组的待收货；普通账号只看到本组 |

### R8 部署与回滚（中危）

| 项 | 内容 |
|---|---|
| 预防 | ①每阶段前 `git tag s1-before` ②部署命令固定用 `(printf '\n'; sleep 10; printf 'Y\n'; sleep 6; printf 'Y\n')`（回车=自动切流，`yes Y` 会选成手动切流导致不生效）③失败先看 `tcb cloudrun logs process --run-id <id>`，不要盲目重试 ④改 `education.py` 后必须 `grep -c "router.include_router"` = 18（曾误删致容器崩溃） |
| 验证 | 每阶段：部署状态 normal + 健康检查 200 + 生免组主要页面逐个点开（清单见 S5） |

### R9 后续批量导入其他组数据（低危，但易污染）

| 项 | 内容 |
|---|---|
| 预防 | 导入脚本必须显式带 `--group=<code>`；导入前备份、导入后核对条数；**禁止**把生免组数据复制到其他组 |
| 验证 | 导入报告（新增/跳过/失败 条数）+ 各模块列表条数核对 |

### R10 汇总类页面的口径（低危）

| 项 | 内容 |
|---|---|
| 规则 | 工作台、汇总维修记录等**只统计当前组**；管理员可选"全院视图"（后续再做）；EQA/质控等模块暂不对其他组开放，故不涉及 |
